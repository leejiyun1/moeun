# Codebase Next Actions

## 문서 목적

이 문서는 관리자 기본 기능, 상품/패키지/시음 구조 정리, 추천 API 1차 교체 이후 남은 작업만 정리한다.

이미 반영된 작업은 이 문서의 해야 할 일 목록에서 제외한다.

코드가 어느 사용자/관리자 흐름에 속하는지는 `docs/SERVICE_FLOW_SPEC.md` 를 기준으로 판단한다.

## 현재 기준

- 상품은 `Product` 공통 껍데기에서 단일 술 `drink` 또는 고정 패키지 `package`를 참조한다.
- 관리자는 단일 상품과 고정 패키지 상품을 등록할 수 있다.
- 패키지 정책은 커스텀 패키지와 고정 패키지 구성 제한에 사용한다.
- 시음 가능 여부는 상품 단위 필드로 관리한다.
- `/api/v1/products/recommended/`는 실제 추천 서비스 `ProductRecommendationService`를 사용한다.
- 검색은 `ProductSearchService`, 추천은 `ProductRecommendationService`로 분리한다.
- 장바구니 추가 API에서 픽업 매장/날짜 하드코딩은 제거했다.
- 주문/수령 방식은 픽업, 배송, 문의형 신청 중 아직 확정되지 않았다.
- 현재 코드에는 픽업 필드가 남아 있지만, 운영 방식 확정 전까지 픽업 전용 기능을 더 확장하지 않는다.

## P0. 운영 흐름에 직접 영향

### 1. 주문/수령 방식 결정 대기

현재 상태:

- 장바구니 API의 고정 픽업 값은 제거했다.
- 백엔드 장바구니 모델은 `pickup_store`, `pickup_date`를 받을 수 있다.
- 일반 장바구니 상품은 프론트 장바구니에서 픽업 매장/날짜를 입력할 수 있다.
- 주문 생성은 프론트가 보낸 선택 장바구니 항목 기준으로 생성된다.
- 선택한 일반 상품에 픽업 정보가 없으면 프론트와 백엔드에서 주문을 막는다.
- 커스텀 패키지 draft는 아직 장바구니 화면에서 충분히 표시/선택되지 않는다.
- 다만 실제 운영 흐름이 픽업 예약인지, 배송 주문인지, 상담/신청형인지 아직 확정되지 않았다.

해야 할 일:

- 담당자 확인 후 주문/수령 방식을 확정한다.
- 확정 전까지 커스텀 패키지 draft를 픽업 전용 UI에 억지로 끼워 넣지 않는다.
- 확정된 방식에 따라 현재 `pickup_store`, `pickup_date` 필드를 유지할지, `fulfillment` 구조로 일반화할지 결정한다.

판단 기준:

- 사용자가 실제 주문을 만들 때 필수 주문/수령 정보 누락이 발생하지 않아야 한다.
- 일반 상품과 커스텀 패키지 모두 선택한 항목만 주문되어야 한다.
- 코드가 특정 수령 방식을 확정된 운영 정책처럼 숨기면 안 된다.

### 2. 운영 데이터 입력 방식 결정

현재 상태:

- 별도 관리자 페이지의 기본 골격은 있다.
- 상품/패키지/정책 등록은 1차로 가능하다.
- 실제 운영 데이터 입력 UX는 아직 충분히 다듬어진 상태가 아니다.

해야 할 일:

- 운영자가 최소한으로 관리해야 할 데이터 범위를 확정한다.
- 상품 이미지 입력 방식, 설명 이미지, 가격/할인, 시음 가능 여부를 관리자에서 안정적으로 관리하게 한다.
- 운영 DB와 데모 DB를 분리할 때 데이터 이관 방식도 같이 정한다.

판단 기준:

- 개발자가 직접 DB를 만지지 않아도 운영자가 기본 상품을 등록할 수 있어야 한다.
- 운영 전환 시 데모 데이터와 운영 데이터를 섞지 않아야 한다.

## P1. 추천 시스템 고도화 전 정리

### 3. 취향 프로필 서비스 분리

현재 문제:

- `TasteProfileView`가 프로필 생성, 분석 필요 여부 판단, 분석 생성, 응답 조립을 많이 담당한다.
- 추천 서비스는 현재 `PreferTasteProfile`을 읽기만 하지만, 취향 프로필 갱신 정책까지 붙으면 view가 더 무거워진다.

해야 할 일:

- `TasteProfileQueryService`: 현재 사용자 취향 프로필 조회, 없을 때 fallback 결정.
- `TasteProfileCommandService`: 테스트 결과 기반 생성, 재테스트 반영, 후기 분석 반영.
- `TasteProfileAnalysisService`: 분석 문구 생성, 갱신 필요 여부 판단.
- `TasteProfileView`: 인증 확인, 서비스 호출, serializer 응답만 담당.

판단 기준:

- 추천 서비스가 취향 프로필을 재사용해도 view 로직에 의존하지 않아야 한다.
- 분석 문구 생성 실패와 프로필 조회 실패를 분리해서 처리할 수 있어야 한다.

### 4. 피드백 저장 side effect 제거

현재 문제:

- `Feedback.save()`가 상품 리뷰 수 증가를 직접 수행한다.
- `Feedback.delete()`도 이미지 삭제와 상품 리뷰 수 감소를 직접 처리한다.
- 모델 저장만으로 다른 도메인 상태가 바뀌어서 운영 장애 추적이 어렵다.

해야 할 일:

- `FeedbackCommandService.create_feedback(...)` 추가.
- `FeedbackCommandService.delete_feedback(...)` 추가.
- 후기 저장, 이미지 저장, 상품 통계 변경을 transaction 안에서 처리한다.
- `Feedback` model은 저장 구조와 기본 제약만 담당하게 줄인다.

판단 기준:

- 피드백 생성/삭제의 부수효과가 서비스 한 곳에서 보인다.
- 취향 학습 정책을 바꿔도 모델 코드를 수정하지 않아야 한다.

### 5. 리뷰 입력 단순화와 후기 텍스트 기반 학습 설계

현재 문제:

- 기존 직접 맛 점수 입력은 술의 객관적 맛 평가인지 사용자의 선호도인지 구분하기 어렵다.
- 입맛 적합도나 신뢰도도 사람이 직접 정확히 판단하기 어렵다.
- 리뷰 입력 부담이 크면 실제 운영에서 데이터가 쌓이기 어렵다.

반영 완료:

- 프론트 리뷰 작성 화면에서 맛별 점수, 입맛 적합도, 신뢰도 입력을 제거했다.
- 프론트는 평점, 후기, 이미지만 API로 전송한다.
- 백엔드 `Feedback`에서 맛별 점수, `confidence`, `selected_tags` 필드를 제거했다.
- 태그 중심 구조로 추가했던 `positive_tags`, `negative_tags`는 제거한다.
- 리뷰 저장 시 사용자 취향 프로필을 자동 갱신하지 않는다.

설계 기준:

- 상세 설계는 `docs/REVIEW_TASTE_LEARNING_DESIGN.md` 를 따른다.
- 사용자는 평점과 후기를 필수로 남기고, 이미지는 선택으로 첨부한다.
- 사용자는 신뢰도, 맛 평가, 입맛 적합도, 태그를 직접 입력하지 않는다.
- 리뷰 저장은 원본 후기를 남기는 일까지만 담당한다.
- 후기 텍스트 분석 실패가 리뷰 저장 실패로 이어지면 안 된다.

해야 할 일:

- `FeedbackCommandService`로 후기 저장 부수효과를 이동한다.
- 후기 텍스트 분석 결과 저장 모델을 설계한다.
- `TasteProfileLearningService` 추가.
- 분석 결과가 충분히 확실한 경우만 입맛 프로필에 소폭 반영한다.

판단 기준:

- 리뷰 작성 화면에 사람이 직접 입력하는 맛별 점수, 입맛 적합도, 신뢰도, 태그가 없어야 한다.
- 리뷰 저장과 입맛 학습이 분리되어야 한다.
- 입맛 프로필 변경 근거가 후기 분석 결과 기준으로 추적 가능해야 한다.

### 6. 추천 scorer 구조 고도화

현재 상태:

- `ProductRecommendationService`는 1차 추천을 수행한다.
- 로그인 사용자는 취향 유사도 기반, 비로그인은 fallback 기준으로 추천한다.
- 단일 상품과 고정 패키지 모두 추천 대상에 포함된다.
- 상세 설계는 `docs/RECOMMENDATION_SYSTEM_DESIGN.md` 를 따른다.

남은 문제:

- 점수 계산, 후보 선택, 추천 이유 생성이 아직 하나의 서비스 안에 있다.
- 후기 추천, 검색 결과 개인화, 추천 문구 개선까지 확장하려면 scorer를 분리하는 편이 좋다.

해야 할 일:

- `RecommendationScorer`: 취향 유사도, 반응도, 운영 가중치 계산.
- `RecommendationCandidateSelector`: 추천 후보 조회.
- `RecommendationReasonBuilder`: 추천 이유 문구 생성.
- `ProductRecommendationService`: 위 구성요소를 조합하는 orchestrator 역할만 담당.

판단 기준:

- 상품 추천과 후기 추천이 같은 맛 유사도 계산을 재사용할 수 있어야 한다.
- 추천 점수 가중치를 바꿀 때 view나 serializer를 수정하지 않아야 한다.

## P2. 프론트/문서 정리

### 7. UI/API 연결 점검

반영 완료:

- 상품 카드, 검색 결과 카드, 상세 대표 이미지의 하트 버튼을 백엔드 상품 좋아요 API에 연결했다.
- 상품 목록/상세 응답에 로그인 사용자의 `is_liked` 상태를 포함한다.
- 검색 결과 카드의 중첩 링크 구조를 제거하고 공통 카드 링크 동작으로 통일했다.
- 실제 API와 맞지 않던 MSW mock과 미사용 UI/유틸 파일을 제거했다.

남은 연결 후보:

- 관리자 상품 목록에는 수정/상태 변경/삭제 UI가 없지만, 백엔드 관리 API는 준비되어 있다.
- 관리자 패키지 정책 목록에는 수정/삭제 UI가 없지만, 백엔드 관리 API는 준비되어 있다.
- 양조장 생성/수정 API는 있으나 별도 관리자 화면은 없다.
- 내 후기 수정/삭제 API는 있으나 마이페이지 UI에는 아직 없다.

판단 기준:

- 화면에 버튼이 있으면 서버 상태와 연결되어야 한다.
- 서버 API만 있고 운영자가 실제로 써야 하는 기능은 관리자 진입점을 추가한다.
- 아직 정책이 확정되지 않은 기능은 화면에 과장해서 노출하지 않는다.

### 8. 프론트 추천 UX 반영

현재 상태:

- 추천 API 응답에는 `recommendation_mode`, `recommendation_score`, `recommendation_reason`이 포함될 수 있다.
- 프론트 타입은 이를 받을 수 있게 확장했다.
- 화면에서는 아직 추천 이유나 개인화/fallback 상태를 적극적으로 보여주지 않는다.

해야 할 일:

- 추천 섹션에서 로그인 사용자에게 “취향 기반 추천” 문구를 보여준다.
- 비로그인/fallback 상태에서는 “인기와 운영 기준 추천”처럼 과장되지 않은 문구를 사용한다.
- 카드에서 `recommendation_reason`을 표시할지, 상세 진입 후 보여줄지 결정한다.

판단 기준:

- 실제 추천이 아닌 경우 개인화처럼 보이게 말하지 않는다.
- 추천 근거가 너무 장황하지 않고 사용자가 바로 이해할 수 있어야 한다.
