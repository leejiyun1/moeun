# Review Taste Learning Design

## 문서 목적

이 문서는 리뷰 작성 흐름에서 사용자의 입맛 프로필을 어떻게 학습할지 정의한다.

핵심은 아래다.

- 리뷰 점수는 술의 객관적 맛 평가가 아니다.
- 리뷰 점수는 `그 맛이 나에게 얼마나 잘 맞았는지`를 나타내는 입맛 적합도다.
- 사용자는 전체 평점과 후기를 필수로 남긴다.
- 6개 맛 축별 입맛 적합도는 선택 입력으로 둔다.
- 입맛 프로필은 확실한 신호만 조금씩 반영한다.

## 기존 방식의 문제

기존 리뷰 구조는 사용자가 `sweetness`, `acidity`, `body`, `carbonation`, `bitterness`, `aroma` 같은 맛 점수를 직접 남겼다.

문제는 이 점수가 무엇을 의미하는지 애매했다.

예:

```text
단맛이 4점인 술에 사용자가 단맛 4점을 남김
```

이 값은 아래 둘 중 무엇인지 구분하기 어렵다.

- 이 술이 달게 느껴졌다.
- 나는 단맛을 좋아한다.

따라서 이 값을 그대로 입맛 프로필에 반영하면 `사용자가 느낀 맛의 강도`와 `사용자의 선호도`가 섞인다.

## 확정 기준

6개 세부 점수의 의미를 바꾼다.

기존 의미:

```text
이 술의 단맛은 몇 점인가요?
```

변경 의미:

```text
이 술의 단맛이 내 입맛에 얼마나 잘 맞았나요?
0점: 전혀 안 맞음
5점: 아주 잘 맞음
건너뛰기: 잘 모르겠음
```

이렇게 하면 점수는 맛의 객관적 강도가 아니라 선호도 신호가 된다.

예:

```text
전체 평점: 5
후기: 달달하고 향이 좋아서 마시기 편했어요.
단맛 적합도: 5
향 적합도: 4.5

해석:
단맛 선호도 소폭 증가
향 선호도 소폭 증가
```

```text
전체 평점: 2
후기: 제 입에는 너무 달아서 부담스러웠어요.
단맛 적합도: 1

해석:
단맛 선호도 소폭 감소
```

## 사용자 입력

필수:

- 전체 평점
- 후기 텍스트

선택:

- 단맛 적합도
- 산미 적합도
- 바디감 적합도
- 탄산감 적합도
- 쓴맛 적합도
- 향 적합도
- 이미지

선택 입력인 이유:

- 사용자가 모든 맛을 명확히 느끼지 못할 수 있다.
- 억지 입력은 학습 품질을 떨어뜨린다.
- 모르겠는 항목은 저장하지 않는 편이 안전하다.

## 데이터 모델 기준

현재 원본 모델은 `Feedback`이다.

유지 필드:

- `rating`: 전체 만족도
- `comment`: 후기 텍스트
- `sweetness`: 단맛 입맛 적합도
- `acidity`: 산미 입맛 적합도
- `body`: 바디감 입맛 적합도
- `carbonation`: 탄산감 입맛 적합도
- `bitterness`: 쓴맛 입맛 적합도
- `aroma`: 향 입맛 적합도
- `image_url`: 후기 이미지
- `selected_tags`: 기존 데이터 호환용 필드

제거 기준:

- `positive_tags`, `negative_tags`는 1차 핵심 구조에서 제외한다.
- 태그는 나중에 후기 UX 보조 수단으로 다시 검토할 수 있지만, 입맛 학습의 중심으로 두지 않는다.

주의:

- DB 필드명은 기존 호환 때문에 `sweetness` 등을 유지한다.
- 코드와 문서에서는 이를 `맛 평가 점수`가 아니라 `입맛 적합도 점수`로 해석한다.

## 처리 흐름

### 1. 리뷰 저장

```text
사용자 리뷰 작성
→ Feedback 저장
→ 상품 review_count 증가
→ 입맛 적합도 입력이 있는 항목만 학습 후보로 사용
```

현재는 `Feedback.save()`가 상품 리뷰 수 증가와 취향 프로필 업데이트를 직접 수행한다.

다음 단계에서는 이 부수효과를 `FeedbackCommandService`로 옮긴다.

### 2. 입맛 프로필 반영

1차 기준:

```text
전체 평점 4~5 + 맛 적합도 4~5
→ 해당 맛 선호도 소폭 증가

전체 평점 1~2 + 맛 적합도 0~2
→ 해당 맛 선호도 소폭 감소

전체 평점 3
→ 기본적으로 반영하지 않거나 매우 약하게 반영
```

반영하지 않는 경우:

- 해당 맛 적합도를 입력하지 않았다.
- 전체 평점과 맛 적합도 방향이 크게 충돌한다.
- 후기 내용이 비어 있다.
- 이미 반영된 리뷰다.

## API 계약

리뷰 작성 요청:

```json
{
  "order_item": 1,
  "rating": 5,
  "comment": "달달하고 향이 좋아서 마시기 편했어요.",
  "sweetness": 5.0,
  "aroma": 4.5
}
```

입력하지 않은 맛 축은 요청에 보내지 않는다.

리뷰 작성 응답:

```json
{
  "id": 10,
  "rating": 5,
  "comment": "달달하고 향이 좋아서 마시기 편했어요.",
  "sweetness": "5.0",
  "aroma": "4.5"
}
```

## 프론트 화면 기준

리뷰 작성 UI:

```text
전체 평점
맛별 입맛 적합도
후기
이미지
```

사용자에게 보여줄 문구:

```text
술의 맛을 객관적으로 평가하는 게 아니라, 내 입맛에 얼마나 잘 맞았는지 선택해주세요.
잘 모르겠는 항목은 건너뛰어도 됩니다.
```

피해야 할 문구:

```text
단맛 점수를 입력해주세요
이 술의 산미는 몇 점인가요
입맛 프로필에 반영할 값을 입력해주세요
```

이유:

- 사용자가 전문가처럼 맛을 평가해야 한다고 느끼면 입력 부담이 커진다.
- 이 서비스에 필요한 값은 객관적 맛 강도가 아니라 개인 적합도다.

## 구현 단계

### 1단계

상태: 진행 중

- 태그 중심 구조 제거
- 6개 맛 축을 입맛 적합도 선택 입력으로 복구
- 프론트 요청에서 입력한 맛 축만 전송
- 백엔드 `positive_tags`, `negative_tags` 제거
- 문서 기준을 입맛 적합도 중심으로 정리

### 2단계

상태: 예정

- `FeedbackCommandService` 추가
- `Feedback.save()` side effect 제거
- 리뷰 저장, 이미지 저장, 상품 통계 변경, 입맛 학습 호출을 transaction으로 묶기

### 3단계

상태: 예정

- `TasteProfileLearningService` 추가
- 전체 평점과 맛별 적합도 방향을 같이 보고 반영
- 반영 delta 제한
- `TasteProfileUpdateLog` 저장

### 4단계

상태: 예정

- 후기 텍스트 분석 연결
- 로컬 LLM 또는 규칙 기반 분석을 보조 신호로 사용
- 분석 실패가 리뷰 저장 실패로 이어지지 않게 분리

## 운영 리스크

### 사용자가 모든 항목을 5점으로 누름

대응:

- 모든 맛 축을 필수로 만들지 않는다.
- 전체 평점과 후기 내용이 약하면 강하게 반영하지 않는다.

### 사용자가 맛을 잘 모르고 입력함

대응:

- 건너뛰기 선택을 명확히 제공한다.
- 입력하지 않은 맛 축은 학습하지 않는다.

### 리뷰 수가 적음

대응:

- 초기에는 취향 테스트 기반 프로필 영향력을 유지한다.
- 리뷰 1개당 변화량을 작게 제한한다.

### 기존 태그 데이터

대응:

- `selected_tags`는 당장 삭제하지 않는다.
- 신규 리뷰 학습에는 사용하지 않는다.
- 기존 후기 표시 호환이 끝나면 제거를 검토한다.
